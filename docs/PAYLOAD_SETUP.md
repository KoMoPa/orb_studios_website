## GraphQL API

### What You Have
Your Payload CMS comes with a built-in **GraphQL endpoint** for querying data. This is fully configured and ready to use.

### Endpoints
- **`POST /api/graphql`** - The main GraphQL endpoint for executing queries and mutations
- **`GET /api/graphql-playground`** - An interactive IDE (like Postman for GraphQL) where you can test queries visually

### How It Works
Both endpoints are auto-generated by Payload using its built-in GraphQL plugin. You don't need to manually create these routes—they're automatically available when your app starts.

### Why Use GraphQL?
- **Typed Schema** - GraphQL introspection gives you type safety and auto-completion
- **Single Request** - Fetch exactly what you need (no over-fetching like REST API)
- **Easy Exploration** - GraphQL Playground lets you explore all available queries
- **Frontend-Friendly** - Can be easily called from frontend components

### Example GraphQL Query
```graphql
query {
  Posts(where: { publishedAt: { exists: true } }, limit: 10) {
    docs {
      id
      title
      slug
      excerpt
      hero {
        id
        filename
        alt
      }
    }
  }
}
```

### Auto-Generated vs Custom
**Auto-generated files** (marked with "DO NOT MODIFY" comments) are regenerated when your Payload config changes. You shouldn't edit them directly.

### What You Could Add
While Payload handles the main GraphQL and REST endpoints, you might want to add custom API routes for:

**Webhooks**
```typescript
// src/app/(payload)/api/webhooks/post-publish/route.ts
export async function POST(request: Request) {
  // Handle post publication events
  // Could trigger emails, cache invalidation, etc.
}
```

**Custom Data Endpoints**
```typescript
// src/app/(payload)/api/custom/featured-posts/route.ts
export async function GET() {
  const payload = await getPayload()
  const posts = await payload.find({
    collection: 'posts',
    where: { featured: { equals: true } }
  })
  return Response.json(posts.docs)
}
```

**Search/Filter Endpoints**
```typescript
// src/app/(payload)/api/search/route.ts
export async function GET(request: Request) {
  const { searchParams } = new URL(request.url)
  const query = searchParams.get('q')
  // Search pages and posts for query
}
```

**Authentication Endpoints**
```typescript
// src/app/(payload)/api/auth/logout/route.ts
export async function POST() {
  // Custom logout logic
}
```

The key: Keep API logic organized in `/api`, use `getPayload()` to query data, and return JSON responses.

## Query Helpers

### Purpose
`queryHelpers.ts` is your **data access layer**—a single file containing all the helper functions you use to fetch data from Payload. This prevents you from scattering `getPayload()` calls throughout your codebase.

### Location
`src/app/(payload)/lib/payload/queryHelpers.ts`

### What's Currently Included
```typescript
getPages()                    // Fetch all published pages
getPageBySlug(slug)           // Fetch a specific page
getPosts(limit = 10)          // Fetch latest published posts
getPostBySlug(slug)           // Fetch a specific post
getNavigation()               // Fetch header navigation global
getFooter()                   // Fetch footer global
getSettings()                 // Fetch settings global
getMedia(id)                  // Fetch a specific media file
```

### Why This Matters
Instead of doing this in components:
```typescript
// ❌ Bad: Repeating getPayload() everywhere
const payload = await getPayload()
const posts = await payload.find({ collection: 'posts', ... })
```

Do this:
```typescript
// ✅ Good: Use the query helper
import { getPosts } from '@/app/(payload)/lib/payload/queryHelpers'
const posts = await getPosts()
```

### What You Should Add
As you build your site, expand this file with more helpers:

```typescript
/**
 * Fetch posts filtered by category
 */
export async function getPostsByCategory(categoryId: string, limit = 10) {
  const payload = await getPayload()
  return await payload.find({
    collection: 'posts',
    where: {
      and: [
        { categories: { equals: categoryId } },
        { publishedAt: { exists: true } }
      ]
    },
    sort: '-publishedAt',
    limit,
  })
}

/**
 * Fetch all categories
 */
export async function getCategories() {
  const payload = await getPayload()
  const result = await payload.find({ collection: 'categories' })
  return result.docs
}

/**
 * Search pages and posts by title
 */
export async function search(query: string) {
  const payload = await getPayload()
  const [pages, posts] = await Promise.all([
    payload.find({
      collection: 'pages',
      where: { title: { contains: query } }
    }),
    payload.find({
      collection: 'posts',
      where: { title: { contains: query } }
    })
  ])
  return { pages: pages.docs, posts: posts.docs }
}

/**
 * Get post count
 */
export async function getPostCount() {
  const payload = await getPayload()
  const result = await payload.find({
    collection: 'posts',
    where: { publishedAt: { exists: true } },
    depth: 0,
  })
  return result.totalDocs
}
```

### Best Practices
- Create one helper per query type
- Always use descriptive names (e.g., `getPostsByCategory`, not `getPosts2`)
- Add JSDoc comments explaining parameters and returns
- Keep related queries together
- Use `depth` parameter to control nested data fetching

## Accessing Payload Instance

### The Singleton Pattern
Your `getPayload()` function implements a **singleton pattern**—it ensures only one Payload instance exists throughout your app.

### How It Works
```typescript
// src/app/(payload)/lib/payload/getPayload.ts
let cached: Payload | null = null

export const getPayload = async (): Promise<Payload> => {
  if (!cached) {
    const { getPayload: getPayloadInstance } = await import('payload')
    cached = await getPayloadInstance({ config })
  }
  return cached
}
```

**First call**: Initializes the Payload instance and caches it  
**Subsequent calls**: Returns the cached instance (fast, no re-initialization)

### Why This Matters
- **Performance**: Initializing Payload is expensive; caching reuses the connection
- **Consistency**: All parts of your app use the same database connection
- **Simplicity**: You don't need to manually manage the lifecycle

### Using It in Your Code
```typescript
// In a Server Component or API Route
import { getPayload } from '@/app/(payload)/lib/payload/getPayload'

export default async function MyPage() {
  const payload = await getPayload()
  
  // Query directly if needed
  const allUsers = await payload.find({ collection: 'users' })
  
  // Or use a helper function
  import { getPages } from '@/app/(payload)/lib/payload/queryHelpers'
  const pages = await getPages()
  
  return <div>{/* render */}</div>
}
```

### Direct API Access
While you should prefer `queryHelpers`, sometimes you need to query directly:
```typescript
const payload = await getPayload()

// Find with conditions
const result = await payload.find({
  collection: 'posts',
  where: {
    and: [
      { publishedAt: { exists: true } },
      { featured: { equals: true } }
    ]
  },
  sort: '-publishedAt',
  depth: 2,
  limit: 5,
  page: 1
})

// Find by ID
const post = await payload.findByID({
  collection: 'posts',
  id: 'some-id'
})

// Find global
const header = await payload.findGlobal({ slug: 'header' })

// Create
const newPost = await payload.create({
  collection: 'posts',
  data: { title: 'New Post', ... }
})
```

## Blocks (Content Components)

### Purpose
Blocks are **reusable content components** that allow editors to build dynamic page layouts in Payload without writing code.

### Current State
Your `src/blocks/` folder is empty—you haven't defined any blocks yet.

### How Blocks Work Step-by-Step

**1. Define a Block** (once in your code)
```typescript
// src/blocks/Hero.ts
import type { Block } from 'payload'

export const HeroBlock: Block = {
  slug: 'hero',
  label: 'Hero',
  fields: [
    { name: 'heading', type: 'text', required: true },
    { name: 'subheading', type: 'textarea' },
    { name: 'backgroundImage', type: 'upload', relationTo: 'media' },
    { name: 'ctaText', type: 'text' },
    { name: 'ctaUrl', type: 'text' }
  ]
}
```

**2. Register in Collections**
```typescript
// src/collections/Pages.ts
fields: [
  { name: 'title', type: 'text', required: true },
  {
    name: 'content',
    type: 'richText',
    editor: defaultLexical,
    // Make it blockable
    blocks: [HeroBlock, CTABlock, GalleryBlock, ...]
  }
]
```

**3. Editor Uses Blocks**
In the Payload admin dashboard, when editing a Page, the editor can:
- Click "Add Block" in the content field
- Choose "Hero", "CTA", "Gallery", etc.
- Fill in the fields for that block
- Save

**4. Data Structure**
The `content` field becomes an array of blocks:
```json
{
  "title": "Home",
  "content": [
    {
      "blockType": "hero",
      "heading": "Welcome",
      "subheading": "Your creative agency",
      "backgroundImage": { "id": "123", "filename": "hero.jpg" }
    },
    {
      "blockType": "cta",
      "text": "Get Started",
      "url": "/contact"
    }
  ]
}
```

**5. Render on Frontend**
In your React component:
```typescript
// components/PageContent.tsx
import { HeroBlockComponent } from './blocks/HeroBlockComponent'
import { CTABlockComponent } from './blocks/CTABlockComponent'

const blockComponents = {
  hero: HeroBlockComponent,
  cta: CTABlockComponent,
  gallery: GalleryBlockComponent,
  // ... map all blocks
}

export function PageContent({ blocks }: { blocks: Block[] }) {
  return (
    <>
      {blocks?.map((block) => {
        const Component = blockComponents[block.blockType]
        return Component ? <Component key={block.id} {...block} /> : null
      })}
    </>
  )
}
```

### What You Should Create
Examples of blocks for your site:
```
src/blocks/
├── Hero.ts          // Full-width hero with image
├── CTASection.ts    // Call-to-action with button
├── TwoColumn.ts     // Two-column layout

├── Testimonials.ts  // Client testimonials
├── Features.ts      // Feature list

```

### Benefits
- ✅ Editors can build pages without code
- ✅ Consistency across your site
- ✅ Easy to maintain and update
- ✅ No HTML knowledge required
- ✅ SEO-friendly structure

## Collections

Collections are **Payload's term for database tables/content types**. Each collection stores a specific type of content.

### Pages

**Purpose**: Standalone web pages on your site (home, about, contact, etc.)

**Fields**:
- `title` - Page name (required)
- `slug` - URL-friendly identifier, must be unique (required)
- `publishedAt` - Publication date (controls draft/published state)
- `content` - Rich text editor for page body (where blocks go)

**Publishing State**:
- Published pages are visible to everyone
- Unpublished (drafts) are only visible to logged-in users
- Access control is built-in via the `publishedAt` field

**Use Cases**:
- Homepage
- About us page
- Contact page
- Services page
- Legal pages (privacy, terms)

**Example Fetch**:
```typescript
const homePage = await getPageBySlug('home')
```

### Posts

**Purpose**: Blog articles or news content (typically published in chronological order)

**Fields**:
- `title` - Post title (required)
- `slug` - URL identifier, must be unique (required)
- `excerpt` - Short summary of the post
- `content` - Rich text editor for full post body
- `hero` - Featured image (upload relationship)
- `categories` - Multiple category tags (relationship)
- `publishedAt` - Publication date

**Why Posts Are Different from Pages**:
- Posts can have multiple **categories**
- Posts have **excerpts** for listing views
- Posts have **hero images** for cards/previews
- Posts are typically displayed chronologically
- Editors expect timestamps on posts

**Use Cases**:
- Blog articles
- News announcements
- Case studies
- Team updates
- Event announcements

**Example Fetch**:
```typescript
const recentPosts = await getPosts(10)
const featuredPost = await getPostBySlug('my-featured-story')
```

### Categories

**Purpose**: Organize posts by topic/tag (lightweight taxonomy)

**Fields**:
- `title` - Category name (required)
- `description` - Optional category description (rich text)

**Important**: Categories are **referenced by Posts**, not the other way around.

**How It Works**:
1. Create a category "Design" in the admin
2. In a Post, link it to the "Design" category
3. Query posts filtered by that category

**Use Cases**:
- Blog: "Design", "Development", "Marketing"
- News: "Updates", "Features", "Security"
- Portfolio: "Web Design", "Branding", "Video"

**Example Fetch**:
```typescript
const categories = await getCategories()
const designPosts = await getPostsByCategory('design-category-id')
```

### Media

**Purpose**: Central repository for all images and videos

**Fields**:
- `alt` - Accessibility description (required)
- `caption` - Optional image caption

**Upload Configuration**:
- Stored in: `public/media/`
- Served at: `/media/filename`
- Auto-generated responsive sizes:
  - **thumbnail**: 400x300px (listings)
  - **card**: 768x512px (featured cards)
  - **tablet**: 1024x768px (full-width on tablet)

**Why Centralize Media**:
- Single source of truth
- Alt text for accessibility
- Automatic responsive variants
- Easy to replace without updating references
- File optimization and compression
- Bandwidth savings with responsive images

**Example Usage in Posts**:
```typescript
const post = await getPostBySlug('my-post')
// post.hero = { 
//   id: '123',
//   filename: 'image.jpg',
//   alt: 'Description',
//   sizes: { thumbnail: '...', card: '...', tablet: '...' }
// }

<img 
  src={post.hero.sizes.card} 
  alt={post.hero.alt}
  width={768}
  height={512}
/>
```

### Users

**Purpose**: Manage CMS administrators and editors

**Fields**:
- `email` - Login identifier (required)
- `name` - Display name
- `roles` - Admin, Editor, or other roles (select multiple)

**Authentication**:
- Email/password login
- Password hashing handled by Payload
- Session management built-in
- Role-based access control (RBAC)

**Current Roles**:
- `admin` - Full access to everything
- `editor` - Can edit content but not settings

**How Access Works**:
The `Header` and `Footer` globals have this access rule:
```typescript
update: async ({ req }) => {
  return req.user?.roles?.includes('admin') || req.user?.roles?.includes('editor')
}
```
This means only admins and editors can update these globals.

## Globals (Header & Footer)

### What Are Globals?
**Globals** are singleton data structures—unlike collections which have multiple documents, globals have exactly **one instance** that applies across your entire site.

### Header Global

**Purpose**: Site-wide header navigation configuration

**Fields**:
```typescript
{
  name: 'nav',
  type: 'array',
  fields: [
    { name: 'label', type: 'text' },  // Display text
    { name: 'url', type: 'text' }     // Link destination
  ]
}
```

**Data Structure**:
```json
{
  "slug": "header",
  "nav": [
    { "label": "Home", "url": "/" },
    { "label": "About", "url": "/about" },
    { "label": "Blog", "url": "/blog" }
  ]
}
```

**Fetch in Frontend**:
```typescript
// components/Header.tsx
import { getNavigation } from '@/app/(payload)/lib/payload/queryHelpers'

export async function Header() {
  const header = await getNavigation()
  
  return (
    <header>
      <nav>
        {header.nav?.map(item => (
          <a key={item.url} href={item.url}>{item.label}</a>
        ))}
      </nav>
    </header>
  )
}
```

### Footer Global

**Purpose**: Site-wide footer configuration

**Fields**:
```typescript
{
  name: 'copyright',
  type: 'text'  // e.g., "© 2024 Orb Studios"
},
{
  name: 'links',
  type: 'array',
  fields: [
    { name: 'label', type: 'text' },
    { name: 'url', type: 'text' }
  ]
}
```

**Data Structure**:
```json
{
  "slug": "footer",
  "copyright": "© 2024 Orb Studios. All rights reserved.",
  "links": [
    { "label": "Privacy Policy", "url": "/privacy" },
    { "label": "Terms of Service", "url": "/terms" }
  ]
}
```

**Fetch in Frontend**:
```typescript
// components/Footer.tsx
import { getFooter } from '@/app/(payload)/lib/payload/queryHelpers'

export async function Footer() {
  const footer = await getFooter()
  
  return (
    <footer>
      <p>{footer.copyright}</p>
      <nav>
        {footer.links?.map(link => (
          <a key={link.url} href={link.url}>{link.label}</a>
        ))}
      </nav>
    </footer>
  )
}
```

### Key Differences from Collections
| Aspect | Collections | Globals |
|--------|-----------|---------|
| Multiple documents | ✅ Yes | ❌ No (exactly 1) |
| Use case | Pages, posts, users | Site-wide settings |
| Fetch method | `payload.find()` | `payload.findGlobal()` |
| Admin UI | List view with search | Single document editor |
| Access control | Per-document | Global setting |

## Client vs Server Components

### The 'use client' Directive

In Next.js 13+, all components are **Server Components by default**. This is a paradigm shift—your components run on the server first, then hydrate on the client.

If you need interactive features, you mark a component with `'use client'` at the top to make it a **Client Component**.

### When to Use 'use client'

**Use Server Components (default) when**:
- Fetching data from Payload
- Rendering static content
- Using secrets (API keys, environment variables)
- Reducing JavaScript sent to browser

**Use 'use client' when**:
- Need interactivity (button clicks, form input, state)
- Using React hooks (useState, useEffect, useContext)
- Using browser APIs (localStorage, geolocation)
- Event listeners needed

### Server Component Example
```typescript
// src/components/PostList.tsx
// ✅ No 'use client' - this is a Server Component

import { getPosts } from '@/app/(payload)/lib/payload/queryHelpers'

export default async function PostList() {
  // Can use async/await directly
  const posts = await getPosts(10)

  // Fetches happen on the server, not client
  return (
    <div>
      {posts.map(post => (
        <PostCard key={post.id} post={post} />
      ))}
    </div>
  )
}
```

### Client Component Example
```typescript
// src/components/SearchBox.tsx
'use client'  // ← Must have this at the top

import { useState } from 'react'

export default function SearchBox() {
  const [query, setQuery] = useState('')
  const [results, setResults] = useState([])

  async function handleSearch() {
    // Can call Server Actions from here
    const data = await searchContent(query)
    setResults(data)
  }

  return (
    <div>
      <input 
        value={query}
        onChange={(e) => setQuery(e.target.value)}
      />
      <button onClick={handleSearch}>Search</button>
    </div>
  )
}
```

### Key Rules

1. **'use client' at the top** - Must be first line in file
```typescript
'use client'  // ✅ Correct
import React from 'react'

// vs

import React from 'react'
'use client'  // ❌ Won't work - not at top
```

2. **Server Components can import Client Components**
```typescript
// ✅ Good: Server Component importing Client Component
import SearchBox from '@/components/SearchBox'  // has 'use client'

export default async function Page() {
  const data = await getData()
  return (
    <div>
      <SearchBox />  {/* Client component works here */}
      <ServerContent data={data} />
    </div>
  )
}
```

3. **Client Components CANNOT import Server Components directly**
```typescript
'use client'
import { ServerFetch } from '@/components/ServerFetch'  // ❌ Error!

// You must pass Server Component content as children
export default function ClientWrapper() {
  return <div>{children}</div>  // Pass server component here
}
```

4. **Server Actions work in both**
```typescript
// src/actions/posts.ts
'use server'

export async function getPosts() { /* ... */ }

---

// Used in Server Component
import { getPosts } from '@/actions/posts'

export default async function ServerPage() {
  const posts = await getPosts()  // ✅ Direct call
  return <div>{/* render */}</div>
}

---

// 'use client'
// Used in Client Component
import { getPosts } from '@/actions/posts'

export default function ClientPage() {
  const [posts, setPosts] = useState([])
  
  async function load() {
    const data = await getPosts()  // ✅ Call from client
    setPosts(data)
  }
  
  return <button onClick={load}>Load Posts</button>
}
```

```
📂 Components Organization

├── PostList.tsx (no 'use client')
├── PostCard.tsx (no 'use client') 
└── Page layout
```

### Common Mistakes

```typescript
// ❌ Bad: Client Component fetching data
'use client'
import { useEffect, useState } from 'react'

export default function Posts() {
  const [posts, setPosts] = useState([])
  
  useEffect(() => {
    // This works but sends Payload logic to client
    fetch('/api/posts').then(r => r.json()).then(setPosts)
  }, [])
}

// ✅ Good: Use Server Action instead
'use client'
import { useEffect, useState } from 'react'
import { getPosts } from '@/actions/posts'

export default function Posts() {
  const [posts, setPosts] = useState([])
  
  useEffect(() => {
    getPosts().then(setPosts)  // Runs on server
  }, [])
}

// ✅ Better: Server Component doesn't need 'use client'
import { getPosts } from '@/app/(payload)/lib/payload/queryHelpers'

export default async function Posts() {
  const posts = await getPosts()  // Awaited directly
  return <div>{/* render */}</div>
}
```

### Performance Impact

**Server Components** (default):
- ✅ No JavaScript sent for component logic
- ✅ Can directly access databases/secrets
- ✅ Safer (API keys never exposed)
- ✅ Better SEO

**Client Components** ('use client'):
- ✅ Enable interactivity
- ⚠️ More JavaScript in bundle
- ⚠️ Cannot access server secrets
- ⚠️ Must use Server Actions for backend calls

**Best Practice**: Keep most components as Server Components. Only add 'use client' when you need interactivity.

## Server Actions

### What Are Server Actions?
**Server Actions** are async functions that run on the server but can be called directly from your client-side React components. They bridge the gap between your frontend and backend without needing to create explicit API routes.

This is a Next.js 13+ feature that makes it incredibly easy to interact with Payload from the frontend.

### Why Use Server Actions with Payload?
- **Direct Backend Access**: Call Payload queries from client components without HTTP overhead
- **Type Safety**: Full TypeScript types on both client and server
- **No API Routes Needed**: Skip the boilerplate of creating `/api/` endpoints
- **Form Integration**: Perfect for form submissions and mutations
- **Progressive Enhancement**: Works with and without JavaScript

### Where They Go
```
src/
├── components/
│   ├── Header.tsx
│   └── ...
├── app/
│   ├── (frontend)/
│   │   ├── page.tsx
│   │   ├── actions.ts          # ← Root-level actions
│   │   └── [slug]/
│   │       └── page.tsx
│   └── (payload)/
│       └── ...
└── actions/                     # ← Organized actions folder (optional)
    ├── posts.ts
    ├── pages.ts
    ├── comments.ts
    └── search.ts
```

### Creating Your First Server Action
```typescript
// src/app/(frontend)/actions.ts
'use server'

import { getPostBySlug, getPosts } from '@/app/(payload)/lib/payload/queryHelpers'

/**
 * Fetch a single post for display
 */
export async function fetchPost(slug: string) {
  try {
    const post = await getPostBySlug(slug)
    return { success: true, post }
  } catch (error) {
    return { success: false, error: 'Failed to fetch post' }
  }
}

/**
 * Search posts and pages
 */
export async function searchContent(query: string) {
  try {
    const payload = await getPayload()
    const [posts, pages] = await Promise.all([
      payload.find({
        collection: 'posts',
        where: { title: { contains: query } },
        limit: 5
      }),
      payload.find({
        collection: 'pages',
        where: { title: { contains: query } },
        limit: 5
      })
    ])
    return { posts: posts.docs, pages: pages.docs }
  } catch (error) {
    return { error: 'Search failed' }
  }
}
```


### Mutations with Server Actions
```typescript
// src/actions/posts.ts
'use server'

import { revalidatePath } from 'next/cache'
import { getPayload } from '@/app/(payload)/lib/payload/getPayload'

/**
 * Create a new comment (if you add comments to posts)
 */
export async function createPostComment(postId: string, data: {
  author: string
  email: string
  content: string
}) {
  try {
    const payload = await getPayload()
    
    const comment = await payload.create({
      collection: 'comments',
      data: {
        post: postId,
        author: data.author,
        email: data.email,
        content: data.content,
      }
    })

    // Revalidate the post page to show new comment
    revalidatePath(`/blog/${postId}`)
    
    return { success: true, comment }
  } catch (error) {
    return { success: false, error: 'Failed to create comment' }
  }
}

/**
 * Subscribe to newsletter
 */
export async function subscribeNewsletter(email: string) {
  try {
    const payload = await getPayload()
    
    const subscriber = await payload.create({
      collection: 'subscribers',
      data: { email, subscribedAt: new Date() }
    })
    
    return { success: true }
  } catch (error) {
    if (error.message.includes('duplicate')) {
      return { success: false, error: 'Already subscribed' }
    }
    return { success: false, error: 'Subscription failed' }
  }
}
```

### Server Actions vs API Routes

| Aspect | Server Actions | API Routes |
|--------|----------------|-----------|
| Definition | `'use server'` function | `/api/route.ts` |
| Call from client | Direct function call | `fetch()` or client library |
| Boilerplate | Minimal | More setup |
| Use case | Mutations, SSR data | REST API, webhooks |
| Authentication | Next.js auth | Manual JWT/session |
| Response format | Native types | JSON |
| Revalidation | Built-in `revalidatePath` | Manual cache busting |

### Best Practices
1. **Keep them focused** - One action per purpose
2. **Handle errors gracefully** - Return `{ success, error }` objects
3. **Use revalidatePath** - Refresh cached data after mutations
4. **Type your data** - Use TypeScript interfaces
5. **Security** - Server actions run on the server, so they're safe for secrets
6. **Organize** - Group related actions in `src/actions/` folder

### Common Patterns
```typescript
// src/actions/utils.ts
export type ActionResult<T = void> = 
  | { success: true; data?: T }
  | { success: false; error: string }

// src/actions/posts.ts
'use server'

export async function likePost(postId: string): Promise<ActionResult> {
  try {
    const payload = await getPayload()
    await payload.update({
      collection: 'posts',
      id: postId,
      data: { likes: { increment: 1 } }
    })
    revalidatePath(`/blog/${postId}`)
    return { success: true }
  } catch (error) {
    return { success: false, error: 'Failed to like post' }
  }
}
```

## PostgreSQL, Drizzle, and Zod

### Overview
While Payload CMS handles most of your content management, you may want to use **PostgreSQL with Drizzle ORM and Zod validation** for:
- Custom application data (separate from Payload collections)
- Complementary features (comments, ratings, analytics)
- Direct database operations with type safety
- Custom business logic

This section explains how to use these technologies alongside Payload.

### PostgreSQL
Payload already uses PostgreSQL as its database. Your custom tables share the same database connection.

**What to Know**:
- Payload manages its tables/schema automatically
- You can add your own custom tables in the same database
- Both Payload and your custom code access the same `DATABASE_URI`
- Use separate schemas or table prefixes to avoid conflicts

### Drizzle ORM

**What It Is**:
Drizzle is a lightweight, TypeScript-first ORM. It provides:
- Type-safe database queries
- SQL migrations
- TypeScript validation at compile time
- Simpler syntax than ORMs like Prisma or Sequelize

**When to Use It**:
- Custom tables needed alongside Payload
- Transactions with your own data
- Complex queries not suitable for Payload's query interface
- Application-specific database operations

### Zod

**What It Is**:
Zod is a TypeScript-first schema validation library. It ensures data conforms to expected shapes.

**When to Use It**:
- Validate Server Action inputs
- Parse form submissions
- Validate API request bodies
- Type-safe data transformation

**Why You Installed It**:
You ran `pnpm install zod`—perfect for validating data flowing in and out of your Server Actions.

### Setting Up Drizzle

**1. Install Drizzle**:
```bash
pnpm add drizzle-orm mysql2
pnpm add -D drizzle-kit
```

**2. Configure Drizzle**:
```typescript
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './src/db/schema.ts',
  out: './src/db/migrations',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URI || '',
  },
})
```

**3. Define Your Schema**:
```typescript
// src/db/schema.ts
import { pgTable, serial, text, timestamp, integer, varchar } from 'drizzle-orm/pg-core'

export const comments = pgTable('comments', {
  id: serial('id').primaryKey(),
  postId: varchar('post_id').notNull(),  // Reference to Payload post
  author: text('author').notNull(),
  email: text('email').notNull(),
  content: text('content').notNull(),
  likes: integer('likes').default(0),
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow(),
})

export const newsletter = pgTable('newsletter_subscribers', {
  id: serial('id').primaryKey(),
  email: varchar('email').unique().notNull(),
  subscribedAt: timestamp('subscribed_at').defaultNow(),
})
```

**4. Create Migrations**:
```bash
pnpm drizzle-kit generate:pg
```

This creates migration files in `src/db/migrations/` that you can review and run.

### Using Drizzle with Zod for Validation

**1. Define Zod Schemas**:
```typescript
// src/db/validation.ts
import { z } from 'zod'

export const CreateCommentSchema = z.object({
  postId: z.string().min(1),
  author: z.string().min(2).max(100),
  email: z.string().email(),
  content: z.string().min(5).max(5000),
})

export type CreateCommentInput = z.infer<typeof CreateCommentSchema>

export const SubscribeSchema = z.object({
  email: z.string().email(),
})

export type SubscribeInput = z.infer<typeof SubscribeSchema>
```

**2. Create Database Helpers**:
```typescript
// src/db/queries.ts
import { db } from './client'
import { comments, newsletter } from './schema'
import { eq, desc } from 'drizzle-orm'

export async function getComments(postId: string) {
  return await db
    .select()
    .from(comments)
    .where(eq(comments.postId, postId))
    .orderBy(desc(comments.createdAt))
}

export async function createComment(data: {
  postId: string
  author: string
  email: string
  content: string
}) {
  return await db.insert(comments).values(data).returning()
}

export async function addNewsletterSubscriber(email: string) {
  return await db
    .insert(newsletter)
    .values({ email })
    .onConflictDoNothing()
    .returning()
}
```

**3. Initialize Drizzle Client**:
```typescript
// src/db/client.ts
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'

const client = postgres(process.env.DATABASE_URI || '')
export const db = drizzle(client)
```

### Using in Server Actions

```typescript
// src/actions/comments.ts
'use server'

import { revalidatePath } from 'next/cache'
import { CreateCommentSchema } from '@/db/validation'
import { createComment } from '@/db/queries'

export async function addComment(formData: FormData, postSlug: string) {
  try {
    const raw = {
      postId: formData.get('postId'),
      author: formData.get('author'),
      email: formData.get('email'),
      content: formData.get('content'),
    }

    // Validate with Zod
    const validated = CreateCommentSchema.parse(raw)

    // Save to Drizzle
    const comment = await createComment(validated)

    // Refresh the page to show new comment
    revalidatePath(`/blog/${postSlug}`)

    return { success: true, comment: comment[0] }
  } catch (error) {
    if (error instanceof z.ZodError) {
      return { 
        success: false, 
        error: 'Validation failed',
        issues: error.issues 
      }
    }
    return { success: false, error: 'Failed to add comment' }
  }
}
```
